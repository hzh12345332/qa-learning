# Day 5 ｜ 测试阶段与类型

> 日期：2026-10-23

## 1. 理论要点

### 1.1 四个测试阶段：重点是「门禁」和「缺陷逃逸」

-  每个阶段的输入/输出（门禁）

| 阶段 | 输入 | 输出 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 单元测试 | 代码 | 单测报告、覆盖率 |覆盖率达标、无失败用例|
| 集成测试 | 已通过单测的模块 | 接口测试报告 | 主要接口通、无阻塞缺陷 |
| 系统测试 | 完整构建版本 | 系统测试报告、缺陷单 | 退出准则达标 |
| 验收测试 | 通过系统测试的版本 | UAT 签署 | 业务方确认可接受 |

- 缺陷逃逸（Defect Escape）

缺陷逃逸 = 本应在早期阶段发现的缺陷，被漏到了后期阶段（甚至生产环境）。

| 逃逸路径 | 说明 |
| --- | --- |
| 需求缺陷漏到开发 | 需求评审没提出来 |
| 编码缺陷漏到测试 | 单测没覆盖 |
| 测试缺陷漏到生产 | 用例没覆盖或回归范围判断错 |

**缺陷逃逸率是衡量测试有效性的核心指标，比"执行了多少用例"有意义得多。**

**补充**

缺陷逃逸率 = 生产环境发现的缺陷数 ÷（测试阶段发现 + 生产发现）

| 指标 | 说明什么 |
| --- | --- |
| 发现 100 个 bug | 可能只是版本本身烂 |
| 生产逃逸 0 个 | 说明测试有效 |

### 1.2 冒烟测试（Smoke Testing）

| 维度 | 内容 |
| --- | --- |
| 目的 | 新版本提测后，快速判断"这个版本值不值得测" |
| 时机 | 开发提测后、正式测试之前 |
| 用例特征 | 少（10–30 条）；快（30 分钟内）；只覆盖主流程，不碰边界和异常 |
| 通过 | 进入正式测试 |
| 不通过 | 直接打回开发，不浪费测试资源 |
| 别名 | BVT（Build Verification Test）、版本验证测试 |

关键认知：**冒烟测试是成本控制手段，不是质量保障手段。** 它的价值不在"发现问题"，而在"尽早止损"

实际做法：很多团队把冒烟做成 CI 自动跑（每次构建后自动执行 10 条核心用例），跑挂了直接通知开发。

### 1.3 回归测试（Regression Testing）

| 维度 | 内容 |
| --- | --- |
| 目的 | 验证修改没有引入新问题、没有破坏原有功能 |
| 触发时机 | 缺陷修复后 / 代码变更后 / 配置环境变更后 / 上线前 |
| 失败处理 | 修复后重跑，直到通过 |

- 回归范围怎么定

| 考虑因素 | 说明 |
| --- | --- |
| 修改点直接影响 | 改了哪个功能，该功能的全部用例 |
| 修改点间接影响 | 调用链上下游 —— 改了工具类，所有调用它的功能都要过 |
| 核心主流程 | 无论改什么，登录/下单/支付必须过 |
| 历史高频缺陷模块 | 以前老出问题的地方，容易再出 |
| 公共组件/基础服务 | 改了影响面大（如公共弹窗、支付网关） |

- 三种回归策略：

| 策略 | 做法 | 适用 | 风险 |
| --- | --- | --- | --- |
| 全量回归 | 跑所有用例 | 大版本、核心模块改动 | 耗时长 |
| 精准回归 | 只跑受影响范围 | 小改动、时间紧 | 范围判断错就漏测 |
| 自动化回归 | 脚本跑 | 重复性高、稳定场景 | 维护成本 |

**关键认知**：精准回归的省时，是用"影响分析能力"换来的。分析错了，省下的时间会以线上事故的形式还回去。

### 1.4 冒烟 vs 回归

| 维度 | 冒烟测试 | 回归测试 |
| --- | --- | --- |
| 时机 | 提测后、正式测试前 | 修改后、上线前 |
| 回答的问题 | 这版本能不能测 | 这次改有没有改坏 |
| 用例数量 | 少（10–30 条） | 多（覆盖受影响范围） |
| 覆盖内容 | 只主流程 | 主流程 + 变更点 + 异常 |
| 执行时长 | 30 分钟内 | 几小时到几天 |
| 失败后果 | 打回开发，不进测试 | 修复后重跑 |
| 执行频率 | 每个版本 1 次 | 每次修改后（可能很多次） |

**冒烟问"能不能测"，回归问"有没有改坏"。**

"冒烟失败了怎么办？" → 直接打回，不进入正式测试。
"回归失败了怎么办" → 修复后继续测，直到通过为止

### 1.5 测试左移 / 测试右移

|  | 左移（Shift Left） | 右移（Shift Right） |
| --- | --- | --- |
| 方向 | 往开发前期移动 | 往生产环境移动 |
| 活动 | 需求评审、设计评审、单测、静态扫描、契约测试 | 灰度发布、线上监控、日志告警、混沌工程、A/B 测试、线上巡检 |
| 防什么 | 防"做错"（需求理解错、设计缺陷） | 防"漏测"（测试环境测不出的问题） |
| 核心价值 | 越早发现越省钱 | 真实流量下的问题只有线上能暴露 |

- 怎么理解测试左移

    在需求和设计阶段就介入评审，把缺陷挡在编码之前。减少因需求不清和设计缺陷导致的缺陷。

### 1.6 敏捷 Scrum 中的测试

**测试出现在哪些会上：**

| 会议 | 测试做什么 |
| --- | --- |
| Backlog 梳理会 | 提问澄清需求 ← 测试价值最容易被看见的地方 |
| Sprint 计划会 | 评估测试工作量、识别风险 |
| 每日站会 | 同步进度、暴露阻塞 |
| Sprint 评审会 | 演示可工作软件、验证验收标准 |
| Sprint 回顾会 | 改进流程（比如"这次回归漏了 XX"） |

**关键差异：**

| 传统瀑布 | 敏捷 Scrum |
| --- | --- |
| 测试是"最后一道关" | 测试每个 Sprint 全程参与 |
| 产出详细用例 | 产出验收标准（AC）+ 检查清单 + 探索式测试 |
| 文档重 | 文档轻，重沟通 |

- 敏捷里测试和开发什么关系？
    "不是上下游，是同一个 Sprint 里的协作者。测试在需求梳理阶段就参与，帮团队把验收标准定清楚。

### 1.7 测试计划的 7 要素

| 要素 | 内容 | 注意 |
| --- | --- | --- |
| 测试范围 | 测什么 | 必须明确写出"不测什么" |
| 测试策略 | 用什么方法、覆盖到什么深度 | 对应你学过的等价类/判定表/场景法 |
| 测试类型 | 功能/性能/兼容/安全…哪些做 | 说清哪些不做及原因 |
| 环境与数据 | 环境配置、测试数据来源 | 谁能提供数据 |
| 进度与人力 | 里程碑、各阶段时间、谁负责 | |
| 进入准则 | 满足什么条件才开始测 | 看1.8 |
| 退出准则 | 满足什么条件才算测完 | 看1.8 |
| 风险与应对 | 可能出什么问题、怎么兜底 | |

**"测什么"不如"明确不测什么"重要。 范围边界写清楚，才能避免上线后扯皮"这块你为什么不测"。**

### 1.8 进入准则 / 退出准则

**进入准则（开始测试的前提）**

- 开发自测通过、冒烟通过
- 需求文档已确认/冻结
- 测试环境与数据已就绪
- 无阻塞级（P0）缺陷未修复
- 版本已提测并记录版本号

**退出准则（测试结束的标准）**

- 用例执行率 100%
- 用例通过率 ≥ 95%（或团队约定值）
- 无 P0/P1 遗留缺陷
- P2 遗留缺陷有明确处理计划
- 新增功能有回归验证记录
- 测试报告已完成

**怎么判断测试可以结束了**

回答退出准则

### 1.9 测试报告的结构

| 部分 | 内容 |
| --- | --- |
| 概述 | 项目背景、测试范围、测试周期、参与人 |
| 执行情况 | 用例总数、执行数、通过/失败数、执行率、通过率 |
| 缺陷统计 | 按模块分布、按 Severity 分布、按状态分布 |
| 遗留缺陷 | 未修复清单 + 影响评估 + 处理计划 |
| 风险与结论 | 存在什么风险、是否建议发布 |

## 2. 复盘

- **最大的收获**：写完任何带固定框架的文档（测试计划、缺陷报告、测试报告），回头数一遍框架的项数：10 秒的动作，能避免"交付了半成品"这种最尴尬的情况。
