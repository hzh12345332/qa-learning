## 一、pytest.ini

### 1.1 四个键各管什么

| 键 | 作用 | 不写的后果 |
| --- | --- | --- |
| testpaths | 不带路径时去哪找测试 | 每次都得写路径 |
| addopts | 自动附加的命令行参数 | 每次都得敲 -q --tb=short |
| pythonpath | 往 sys.path 里加目录（pytest 7+ 内置） | import asserts 找不到（见 2.5） |
| markers | 注册自定义标记 | --markers 里看不到，-m smoke 会报 PytestUnknownMarkWarning |

### 2.2 三步接线

**输入：**

```py
import pytest
import json

def pytest_addoption(parser):
    """注册自定义命令行参数"""
    parser.addoption("--env", default="test", choices=["test", "prod"],
                     help="选哪份配置:test / prod")


@pytest.fixture(scope="session")
def env(request):
    """把命令行参数变成 fixture"""
    return request.config.getoption("--env")

@pytest.fixture(scope="session")
def cfg(env):
    path = "week05/day34/config/%s.json" % env
    with open(path, encoding="utf-8") as f:
        data = json.load(f)
    print("\n[cfg] 加载了 %s → %s" % (path, data))    # 整个进程只打一次
    return data
```

**数据流图：**

```text

   ↓ pytest_addoption 注册
request.config.getoption("--env")   → "prod"
   ↓ env fixture
"week05/day34/config/prod.json"      ← 拼路径
   ↓ cfg fixture
{ "baseUrl": ..., "timeout": 30, ... }
```

## 三、三层断言

### 3.1 一条断言说不清的五种原因

| 可能的原因 | 一句话断言能指出吗 |
| --- | --- |
| 接口 500 了 | ✅ 能 |
| 返回的不是 JSON（网关吐了个 HTML 错误页） | ❌ 报的是"解析失败"，看不出根因 |
| 少了关键字段 data | ❌ 得先去翻响应体 |
| 字段在，但值是 null | ❌ 同上 |
| 值不对（期望 1，实际 3） | ❌ 只说"断言失败" |

### 3.2 三层各管什么、为什么按顺序

| 层 | 例子 | 挂了说明什么 | 该找谁 |
| --- | --- | --- | --- |
| 1 传输 | status_code == 200 | 服务没通 / 路由错 / 500 | 后端 / 运维 |
| 2 结构 | 是 JSON、有 data 字段 | 契约变了 / 网关拦截 | 后端 / 接口文档 |
| 3 业务 | data.userId == "1" | 逻辑错了 | 后端 / 前端传参 |

- 因为只有 1 先通过了，2 才能解析并查询字段，3 才可以检查值

## 四、失败快照

### 4.1 两个钩子 + 一个技巧

**钩子：**

- pytest_runtest_makereport 在每条用例结束、生成报告时被调用。

```py
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    rep = outcome.get_result()
    if rep.failed:
        ...把快照塞进 rep.sections...
```

**技巧：**

- requests.Session 有 hooks，每个响应都会过一遍你的函数。

```py
s = requests.Session()
s.hooks["response"].append(lambda resp, *a, **kw: 记一笔)
```

### 4.2 完整实现

| 细节 | 为什么 |
| --- | --- |
| request.node._trace = [] | 记录要挂在当前这条用例上，不能挂在 fixture 自己身上 |
| s.hooks["response"].append(record) | 用 Session 的钩子，不用改测试代码 —— 所有请求自动被记 |
| rep.sections.append((标题, 内容)) | 这是 pytest 官方的"往报告里加一段"接口 |

### 4.4 为什么 client 从 session 降到 function

| 方面 | session 级（昨天） | function 级（今天） |
| --- | --- | --- |
| 连接复用 | ✅ 一个 Session 跑到底 | ❌ 每条用例新 Session |
| 请求记录 | ❌ 混在一起，分不清是哪条的 | ✅ 每条用例天然一份 |
| 状态隔离 | ❌ cookie/headers 会串 | ✅ 干净 |
| 快慢 | 快 | 慢一点点（httpbin 上没感觉） |

| 1 | pytest.ini 的 testpaths / addopts / pythonpath / markers 各管什么 | `testpaths` ：不带路径时去哪找测试；`addopts` ：自动附加的命令行参数；`pythonpath` ：往 sys.path 里加目录；`markers` ：注册自定义标记 |

| 3 | Interrupted: 1 error during collection 和 FAILED 的区别 | `Interrupted` 是收集过程中出错导致整轮停止。`FAILED` 是用例失败，不会影响其他用例执行 |
| 4 | --env 从命令行到 cfg 的数据流（三步） | 1.注册自定义命令行参数。2.把命令行参数变成 fixture。3.配置文件名从 env 拼出来 |

| 6 | 三层断言各管什么，为什么状态码必须第一个 | 第一层：状态码。第二层：响应体结构和字段。第三层：业务。因为如果状态码没过，后面的都排查不了 |
| 7 | [结构层] 报错为什么要把"实际有哪些字段"列出来 | 这样方便排查是少了哪些字段 |
| 8 | 失败快照的两个钩子分别在哪一步起作用 | ① `requests.Session.hooks["response"]`：每个响应回来就记一条（方法/URL/状态码）② `pytest_runtest_makereport`：用例结束时检查 `rep.failed`，失败就把记录 `append` 到 `rep.sections` |
| 9 | client 为什么从 session 级降到 function 级 | 1.需要每条用例的请求记录天然一份。2.需要状态隔离 |
| 10 | request.config.getoption() 和 getini() 的区别 | `request.config.getoption()` ：读取命令行命令。`getini()` ：读 `pytest.ini` |
