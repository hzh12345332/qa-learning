## 关键认知

SauceDemo 是 Sauce Labs 提供的**测试练习站**。它的 6 个账户不是随便起的，每一个都对应一类**预先植入的缺陷**：

| 账户 | 设计意图 |
| --- | --- |
| standard_user | 正常用户，功能应全部正常 |
| locked_out_user | 被锁定账户，用于练负向测试 |
| problem_user | 植入功能与界面缺陷 |
| performance_glitch_user | 植入性能问题（故意拖慢） |
| error_user | 植入报错与校验缺陷 |
| visual_user | 植入视觉与数据缺陷 |

这解释了一个"巧合"：**为什么问题如此整齐地按账户分布**。所以本次找到的缺陷绝大多数是"故意放置"的，这不是运气，而是这个站点的用途所在——它的价值是**让练习者可以验证自己的判断**（找到的就是对的，漏掉的就是漏了）。

**但必须清醒认识它与真实产品的差别**：真实项目里没有"标准答案"，测试人员 90% 的时间花在**"这到底算不算缺陷"**的判断上，而不是"找不找得到"。因此这次练习真正要练的能力是——**把现象描述到别人能精确复现**。

## 二、改进建议（非缺陷，4 条）

> 判断依据：产品功能本身工作正常，只是"不好用"或"功能缺失"，**没有明确的对错标准**。

#### S-01 ｜ 商品图片无法放大查看

- 现象：商品图片无法点击放大
- 影响：用户无法看清商品细节
- 类型：体验 / 易用性

#### S-02 ｜ 商品不支持选择尺码

- 现象：商品详情页没有尺码选择项
- 影响：服装类商品无法完成真实购买流程
- 类型：功能缺失

#### S-03 ｜ 购物车不支持增减商品数量

- 现象：购物车中无法增加或减少商品数量
- 影响：用户只能删除后重新添加
- 类型：功能缺失

#### S-04 ｜ 错误提示文案不可操作

- 现象：错误提示为 `Epic sadface: Sorry, this user has been locked out.` / `Sorting is broken! This error has been reported to Backtrace`
- 存在的三个问题：
  1. `Epic sadface:` 属于内部趣味文案，不应出现在面向用户的提示中
  2. 只说明"出了什么问题"，**没有告诉用户下一步该做什么**（联系谁？等多久？如何解锁？）
  3. 未提供错误码或联系方式，用户无法自助求助
- 预期：错误提示应包含「发生了什么 + 用户可以做什么」
- 类型：易用性 / 文案

#### E-01 ｜ 点击 About 跳转外部站点返回 403

- 现象：点击 About 后显示 403 错误
- 判断：About 跳转的是外部站点（Sauce Labs 官网），403 很可能由网络环境或地区限制导致，**不属于被测产品自身的缺陷**
- 处理：**不列入缺陷统计**；如需确认，可更换网络环境复测

```text
复现步骤：
  1. 点击左上角菜单图标
  2. 点击 Reset App State
  3. 观察右上角购物车图标上的数字
预期结果：购物车角标消失（或显示 0）
实际结果：【待补】
```

## 六、执行通过的用例（1 条）

#### P-01 ｜ 已锁定账户登录应被拒绝

| 项目 | 内容 |
| --- | --- |
| 用例编号 | TC-LOGIN-012 |
| 所属模块 | 登录 |
| 前置条件 | 无（**不需要任何登录状态**） |
| 测试数据 | Username = `locked_out_user`，Password = `secret_sauce` |
| 操作步骤 | 1. 打开登录页 2. 输入上述账号密码 3. 点击 LOGIN |
| 预期结果 | 停留在登录页不跳转；出现错误提示 `Epic sadface: Sorry, this user has been locked out.` |
| **实际结果** | **页面未跳转，显示 `Epic sadface: Sorry, this user has been locked out.`，文案与预期完全一致** |
| **执行结论** | ✅ **通过** —— 锁定机制工作正常 |
| 优先级 | P1 |

**这是一条负向测试用例，认知要点：**

| | 正向测试 | 负向测试 |
| --- | --- | --- |
| 目的 | 验证正常输入能得到正常结果 | 验证非法 / 异常输入被**正确拒绝** |
| 预期 | 操作成功 | 操作失败 + 出现正确的错误提示 |
| 通过条件 | 成功 = 通过 | **失败 = 通过** |

> **判断标准只有一句：测试通过 = 实际结果符合预期结果，而不是"操作成功了"。**

同时说明：**通过的用例同样必须记录**，原因有二——

1. 测试报告需要统计数据（例如"执行 120 条，通过 108 条，失败 12 条"），没有通过记录就出不了报告
2. 通过的用例是**回归基线**，下次版本更新后才能判断"这次是不是改坏了"
