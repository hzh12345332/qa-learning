## 二、鉴权与参数化

### 2.1 三条链路各验证什么

| 请求 | 链路 | 验证的能力 |
| --- | --- | --- |
| 01 / 02 | 无凭证 401 → 带 Bearer 200 | 鉴权是否真的生效 |
| 04 | 无 Cookie → 空对象 | 凭证缺省时的行为 |
| 05 → 06 | 拿 uuid → 传 uuid | 变量在请求之间传递 |

### 2.2 02 的 token 兜底（集合变量 vs 环境变量）

- 之前`token`在环境变量里，不会随着导出入库，别人换环境跑会标红报错
- 集合变量会随集合一起导出，但导出的是 initial value；所以必须填 initial，否则导出的仍是空值（这次就踩到了）。

### 2.3 03 改了什么 body、断言怎么验回显

**新改的body：**

```bash
{
  "name": "张三",
  "age": 18,
  "tags": ["qa", "api"]
}
```

**断言回显：**

```text
passed 状态码是200
passed 服务器收到的是 POST
passed 响应结构符合 schema
passed 回显的 name 和我发的一致
passed 回显的 tags 是数组且长度为 2
```

### 2.4 04 / 04b 一对（无 cookie vs 有 cookie）

**04 无cookie输出：**

```js
{
    "cookies": {}
}
```

**04b 有 cookie输入：**

```text
请求行：GET {{baseUrl}}/cookies
Headers 加一行：
  Key:   Cookie
  Value: session=abc123
```

**04b 有 cookie输出：**

```js
{
    "cookies": {
        "session": "abc123"
    }
}
```

### 2.5 06 依赖 05 的顺序风险

- 风险：Runner 是按集合顺序跑的。如果谁把 06 拖到 05 前面 → 06 必挂。
- 解决方法：在 06 的 Scripts → Before request 加一句前置检查：

```js
if (!pm.collectionVariables.get("uid")) {
    console.warn("uid 为空：06 必须在 05 之后跑");
}
```

### 3.3 删掉哪条断言会让"接口坏了"没人发现

**答：`01` 的「失败响应里不能有 token」**（或 `08` 的「错误响应没有 body」）。

- 删掉「状态码是 401」→ 还有「不含 token」能发现一部分问题
- 删掉「不含 token」→ **401 里泄露 token 这件事，没有任何断言能发现**
- 因为它是**唯一**覆盖“安全泄露”这个维度的断言

**判据**：对每条断言问 —— **删掉它，哪一类问题就没人发现了？**
答不上来，说明这条断言是冗余的（或者写错了层）。
