# SQL 解题方法（Day 13 起用）

> 用途：解决「思路有了，但写不出 SQL」。
> 做题时**按顺序**用这三件工具：① 一行代表什么 → ② 敲骨架空壳 → ③ 填片段。
> 每道题 3 分钟，比抄答案有用。

---

## 0. 先认清自己的卡点（三种，练法完全不同）

| 卡点 | 表现 | 练什么 |
|---|---|---|
| **A 片段不会写** | 知道要"算长度"，不知道写 `CHAR_LENGTH(x)` | 片段卡片（第 3 节） |
| **B 片段拼不起来** | 知道四步，不知道谁在谁前面、分组该放哪 | **骨架默写**（第 2 节） |
| **C 思路没落到"行"上** | 想的是"进程用时"，没想"一行代表什么" | 第 1 节那句问话 |

**大部分时候卡的是 B 和 C，不是 A。** 所以别一卡就去看答案 —— 先确认自己卡在哪一类。

---

## 1. 第一步：先写一句「一行代表什么」

读题之后、写 SQL 之前，**强制自己写一句话**：

```
结果表的每一行代表一个 ________。
```

### 三个真实例子

| 题 | 这句话 | 结论 |
|---|---|---|
| 1581 进店未交易 | 一行 = 一次"没交易的光顾" | `FROM Visits`（光顾的事实在这） |
| 1661 进程平均耗时 | 目标单位 = 一个进程任务；**但表里一行 = 一个事件（start 或 end）** | **一行 ≠ 单位 → 必须先合行** |
| 1068 产品销售额 | 一行 = 一条销售记录 | `FROM Sales` |

### 判据表

| 一行 == 我要的单位？ | 做法 |
|---|---|
| **是** | 直接 `WHERE` + `GROUP BY` |
| **不是**（一行只是零件） | **先合行**：自连接（两行并排）或条件聚合（压成一行） |

> **"一行 ≠ 单位"是最高频的隐形坑。** 1661 卡的就是这个 —— 不是语法问题。

### 顺带定主表

| 题目说法 | 主表 |
|---|---|
| "每位 / 每个 / 所有 X" | **X 的表** |
| "没有做 Y 的 X" / "从未" | **X 的表**（Y 的表里根本没有这些行，不能当主表） |
| "X 的次数 / 个数 / 平均" | X 的表（粒度对才数得对） |

## 2. 第二步：先敲 7 行空壳，再填空

```sql
SELECT   -- 要输出哪些列（含别名、ROUND、聚合函数）
FROM     -- 哪张表做主表（决定"一行代表什么"）
-- JOIN  -- 挂什么表；配对键是什么；角色（start/end）怎么分
-- WHERE -- 行级筛选（★ 不能放聚合函数）
-- GROUP BY -- 按什么分组（"每个/次数/平均"必须有）
-- HAVING -- 组级筛选（★ 可以放聚合函数）
-- ORDER BY -- 排序
```

**空壳的作用：逼每个想法归位。** 写完看一眼——哪一行是空的？空的那行就是漏掉的阶段。

### 2.1 常见「放错位置」

| 想法 | 该放哪 | 放错了会怎样 |
|---|---|---|
| 判 NULL | `WHERE` 或 `ON` | 写到 SELECT 里就变成一列 |
| "每个顾客" | `GROUP BY` | 忘了它 → 结果只有一行或报错 |
| "至少 2 次" | `HAVING` | 写成 `WHERE COUNT(*)>=2` → 语法错 |
| 配对条件（同一机器同一进程） | `ON` | 挪到 `WHERE` 会让 `LEFT JOIN` 退化 |

### 2.2 每个子句后面跟什么（参数类型）

| 子句 | 后面跟什么 | 参数类型 | 能用聚合 | 能用别名 |
|---|---|---|---|---|
| `SELECT` | 列名、表达式、聚合函数、标量子查询 | **输出项列表**（逗号分隔） | ✅ | — |
| `FROM` | 表名，或子查询（**子查询必须起别名**） | 数据源 | — | — |
| `JOIN` | **表名 + 别名**（不是条件！条件在 ON 里） | 数据源 | — | — |
| `ON` | **布尔表达式**（连接条件） | 条件 | ❌ 一般不用 | ❌ |
| `WHERE` | **布尔表达式** | 条件（行级） | ❌ **禁止** | ❌ |
| `GROUP BY` | 列名 / 表达式 / 别名（别名是 MySQL 扩展） | **分组键**（可多个） | ❌ | MySQL 允许 |
| `HAVING` | **布尔表达式**（可含聚合） | 条件（组级） | ✅ **允许** | MySQL 允许 |
| `ORDER BY` | 列名 / 表达式 / 别名 / 序号 | 排序键 | ✅（不推荐） | ✅ |
| `LIMIT` | 整数，或 `偏移, 数量` | 数量 | — | ❌ |

### 2.3 「条件」和「值」是两种东西（最容易混的一层）

**`WHERE` / `HAVING` / `ON` 后面要的是「能判真假的条件」，不是「一个值」。**

条件能长成什么样（只有这些形态）：

```sql
列 = 值                          列 <> 值        列 != 值
列 > 值   列 >= 值   列 < 值   列 <= 值
列 IS NULL                       列 IS NOT NULL
列 BETWEEN a AND b
列 IN (值1, 值2, ...)            列 IN (子查询)
列 LIKE '模式'
列 = (标量子查询)
EXISTS (子查询)                   NOT EXISTS (子查询)
-- 以上任意几条，用 AND / OR / NOT 组合
```

值能是什么：

```sql
数字   42   3.14          字符串   'boring'  '2026-11-04'
NULL                      列名     u.user_id
表达式  rating / position          units * price
函数    CHAR_LENGTH(x)   DATE_ADD(d, INTERVAL 1 DAY)
标量子查询  (SELECT COUNT(*) FROM Users)
```

> **规律：值可以被计算、被比较；条件只能被判真假、用来筛。**

**同一个错误，三种长相**（都出在这条上）：

```sql
WHERE description NOT 'boring'        -- ❌ 条件位置写了"值"
WHERE COUNT(*) > 5                    -- ❌ 条件位置用了聚合（聚合还没算）
SUM(IF(DATEDIFF(a,b)) = 0, 1, 0)      -- ❌ IF 第一个参数应是条件，不是值
```

### 2.4 子查询放在 `WHERE` 后面的五种角色

| 写法 | 子查询必须返回 | 作用 |
|---|---|---|
| `列 = (子查询)` / `> (子查询)` | **1 行 1 列**（标量） | 拿**一个值**来比 |
| `列 IN (子查询)` | **1 列多行** | 判断**在不在这个集合里** |
| `列 > ALL/ANY (子查询)` | 1 列多行 | 和集合里**每个值**都比 |
| `EXISTS (子查询)` | 有几行都行 | 判断**存不存在**关联行（不放大行数） |
| `列 = (子查询 WHERE 内层.键 = 外层.键)` | 1 行 1 列，但**依赖外层** | **相关子查询**：外层每行各算一次 |

**形状不匹配的报错**：

| 形状不对 | 报错 |
|---|---|
| 标量位置给了多行 | `ERROR 1242: Subquery returns more than 1 row` |
| `IN` 位置给了多列 | `Operand should contain 1 column(s)` |
| 相关子查询忘了关联条件 | **不报错**，但每行都得到同一个值（静默错） |

### 2.5 为什么「执行顺序」能解释一切

```
逻辑执行顺序：
FROM → JOIN → ON → WHERE → GROUP BY → 聚合 → HAVING
     → SELECT → DISTINCT → ORDER BY → LIMIT
```

| 现象 | 由哪一步决定 |
|---|---|
| `WHERE` 里**不能用聚合** | 聚合在 `GROUP BY` 之后才算，`WHERE` 比它早 |
| `WHERE` 里**不能用 SELECT 别名** | 别名在 `SELECT` 阶段才产生 |
| `HAVING` **可以用聚合** | 聚合已算完 |
| `ORDER BY` **能用别名 / 能排没选出的列** | 它在 `SELECT` 之后 |
| `ON` 条件挪到 `WHERE` 会让 `LEFT JOIN` **退化** | `ON` 管"配不配"，`WHERE` 管"留不留"，`WHERE` 在 `ON` 之后 |
| `LIMIT` 放最后 | 排完序才截断 |
| 相关子查询能引用外层别名 | 外层那一行已确定，子查询是针对那一行跑的 |
| 多写一个 `JOIN` 却没写 `ON` | 配对条件为空 → 笛卡尔积 |

**但要区分两件事**：

| | 逻辑顺序（语义） | 物理执行（优化器） |
|---|---|---|
| 决定 | **能不能这么写**、结果对不对 | **跑得快不快** |
| 会不会变 | 永远一样 | 因数据量 / 索引 / 版本而变 |

> 执行顺序用来**判断写法合法性**，不要用来推测性能 —— 性能看 `EXPLAIN`。

**它够不够用？**

| 想解决 | 靠什么 |
|---|---|
| 这段想法该放**哪个子句** | ✅ 执行顺序（本章） |
| 这个子句里该写**哪个函数/写法** | ❌ 靠片段积累（第 3 节） |
| 该用 **JOIN 还是子查询** | ❌ 靠判据（第 1 节 + 第 5 节） |

> **执行顺序是地图，片段是工具。有地图知道往哪走，没工具照样动不了手。**

## 3. 第三步：填片段（片段卡片）

**只记自己卡过的，别抄语法书。**

| 场景 | 片段 |
|---|---|
| 判空 | `x IS NULL` / `x IS NOT NULL`（**不是** `= NULL`） |
| 判"没连上" | `右表主键 IS NULL` |
| 字符长度 | `CHAR_LENGTH(s) > 15`（不是 `s > 15`！） |
| 字节长度 | `LENGTH(s)`（中文 UTF-8 占 3 字节） |
| 天数差 | `DATEDIFF(a, b)` = **a − b** |
| 日期加减 | `DATE_SUB(d, INTERVAL 1 DAY)` |
| 计数（行） | `COUNT(*)` |
| 计数（去重个体） | `COUNT(DISTINCT 列)` |
| 条件聚合 | `SUM(CASE WHEN c THEN 1 ELSE 0 END)` |
| 一正一负合并 | `SUM(CASE WHEN type='end' THEN ts ELSE -ts END)` |
| 小数位 | `ROUND(x, 3)` |
| 前 N 行 | `LIMIT n`；跳过前 m 行取 n 行：`LIMIT n OFFSET m` |
| 取前 3 个字符 | `LEFT(s, 3)` |
| 字符串拼接 | `CONCAT(a, b)` |
| 空值替换 | `IFNULL(x, 0)` / `COALESCE(x, 0)` |
| 数"某列的值出现几次" | GROUP BY 该列 + HAVING COUNT(*) >= n（不需要自连接） |
| 同字段多种取值分别计数 | SUM(条件) / COUNT(*) 或 SUM(CASE WHEN ... THEN 1 ELSE 0 END) |
| 比率 = 分子/分母，分母可能为 0 | ROUND(IFNULL(分子/分母, 0), 2) |
| 除法报 0/NULL 或行数变多 | 检查分母是不是 COUNT(*)、是不是连了两次同一张表（需 DISTINCT） |
| 判断奇数 | id % 2 = 1（负数用 MOD(id,2) <> 0） |
| 判断偶数 | id % 2 = 0 |
| 否定一个条件 | description <> 'boring' / NOT (description = 'boring')；NOT 不能直接接值 |
| 加权平均 | SUM(值 * 权重) / SUM(权重)   —— 不能用 AVG |
| 按日期取对应价格 | JOIN ... ON u.date BETWEEN p.start_date AND p.end_date（★条件放 ON） |
| 分母可能为 0 | IFNULL(分子/分母, 0) |
| 占比/率，分母是"全表总数" | ROUND(COUNT(*) / (SELECT COUNT(*) FROM 表) * 100, 2) |
| 分母是"组内的" | 直接 COUNT(...)，同一条 SELECT 里就够 |
| 数"满足条件的行" | SUM(条件)  或  COUNT(CASE WHEN 条件 THEN 1 END)（★不能写 COUNT(布尔表达式)） |
| 数"某列非空的行" | COUNT(列)；COUNT(*) 是数所有行 |
| 比率的分母是"本组行数" | COUNT(*)，不要开子查询 |
| 取年月 'YYYY-MM' | DATE_FORMAT(d, '%Y-%m')  （不是 MONTH(d)） |
| 一行里出多个指标 | 条件聚合：COUNT(*) / SUM(条件) / SUM(值) / SUM(IF(条件, 值, 0)) |
| 条件求和别丢 ELSE | SUM(IF(条件, 值, 0))，写成 NULL 会让整组变 NULL |
| 条件计数 | SUM(条件)  或  SUM(IF(条件, 1, 0))  或  SUM(CASE WHEN 条件 THEN 1 ELSE 0 END) |
| 判断两个日期同一天 | d1 = d2（不要写 DATEDIFF(d1,d2) = 0，多此一举且影响索引） |
| IF 的语法 | IF(条件, 成立值, 不成立值) —— 条件必须在第一个参数里，不能写到括号外面 |
| 取"每个 X 的最早/最新那条" | WHERE (X, 日期) IN (SELECT X, MIN(日期) FROM 表 GROUP BY X) |
| 分子分母必须同口径 | 先用 WHERE 把行筛成同一个集合，再算比例 |
| 分母的判断 | 在当前行集合里能数出来 → COUNT(*)；是"外面世界的数"→ 子查询 |
| 每个键的极值（首次/最后一次） | (键, 日期) IN (SELECT 键, MIN(日期) FROM 表 GROUP BY 键) —— 必须两列一起匹配 |
| 首次之后再加 N 天 | DATE_ADD(MIN(日期), INTERVAL N DAY) |
| "比率"类题的分母 | 题目说"总X数"就是全表 COUNT(DISTINCT X)，不要只数符合条件的 |
| "只在/仅/全部" 某范围内 | ① NOT EXISTS (反例) ② GROUP BY ... HAVING MIN>=a AND MAX<=b |
| SQL 没有 FORALL | "全部满足" = "不存在一条不满足" |
| LEFT JOIN 后 WHERE 写右表列 | 等于写成了 INNER，先想清楚是不是该换 JOIN |
| GROUP BY 要不要写 | 用了聚合函数做"每组判断"就必须写；HAVING 里的 MIN/MAX 就是信号 |
| GROUP BY 写哪几列 | 唯一键 + SELECT 里所有非聚合列（MySQL 的主键函数依赖是宽容，不是标准） |
| 结果一样是不是就等价 | 不是。判据是"数据变了还对不对"，不是"现在跑得通" |
| 子查询当表用 | FROM ( SELECT ... ) t   —— 括号里要完整 SELECT，别名不能省 |
| 想让 WHERE 用上 SELECT 的别名/窗口函数 | 包一层：FROM ( SELECT ..., 窗口函数 AS rk ) t WHERE rk <= n |
| 排名三函数 | ROW_NUMBER 不重复 / RANK 跳号 / DENSE_RANK 不跳号（"前N高"用它） |
| 窗口的分区 | OVER (PARTITION BY 组 ORDER BY 序) —— 分区决定"跟谁比"，排序决定"谁第一" |
| CTE 写法 | WITH 名字 AS ( 完整SELECT ) SELECT ... FROM 名字 |
| 别名跨层吗 | 不跨。CTE 输出只有列名；外层要表就重新起别名 |
| CTE 里的计算列 | 必须 AS 起名，否则外层没法引用 |
| 力扣 185 | 别用 SELECT *（会多带 rk 列），显式列出 3 列并按 Output 对齐大小写 |
| 输出展示名（部门名/用户名/商品名） | 一定要 JOIN 维度表，别直接输出 id |
| PARTITION BY / GROUP BY 用哪列 | 唯一键（departmentId），不用 name（同名会合并） |
| 列名大小写 | MySQL 列名不区分大小写；但表名/别名在 Linux 上区分 —— 别依赖"不报错" |
| "最后一个" + 累计/阈值 | WHERE 累计 <= N ORDER BY 累计 DESC LIMIT 1（不是 = N） |
| 数字列比较 | 数字不加引号：tw <= 1000；加引号就是隐式转换（1683 的坑） |
| 累计求和 | SUM(x) OVER (ORDER BY 排序列) —— 默认 RANGE，逐行要写 ROWS BETWEEN |
| 窗口 vs 自连接 | 窗口"一次算完"，自连接要 "把前面的行都连上" |
| "连续出现 N 次" | ① 自连接 N 次（id = id+1 + num 相同）② GROUP BY num, id-ROW_NUMBER() HAVING COUNT>=N |
| 连续怎么表达 | 先找顺序载体（自增 id / 日期），再用 "+1" 或 "DATEDIFF=1" 表示相邻 |
| 自连接解法必加 | SELECT DISTINCT（连续 5 次会被匹配 3 次） |
| 差值分组技巧 | id - ROW_NUMBER() OVER (PARTITION BY 值 ORDER BY 序) 相同的行 = 连续段 |
| 结果可能为空但要返回 NULL | 外层包标量子查询：SELECT (子查询) AS 列 |
| 取第 N 高（不同值） | SELECT DISTINCT 列 ORDER BY 列 DESC LIMIT 1 OFFSET (N-1) |
| 取第二高（最快） | SELECT MAX(列) WHERE 列 < (SELECT MAX(列) FROM 表) —— 天然去重 + 天然返 NULL |
| 聚合 + 空集 | MAX/MIN/SUM/AVG 返回 NULL，COUNT 返回 0 |
| 判断"某 id 不在表里" | manager_id NOT IN (SELECT id FROM 表) 或 NOT EXISTS (...) |
| NOT IN vs NOT EXISTS 的 NULL | NOT IN：外层 NULL → 被排除；NOT EXISTS：外层 NULL → 判定为"不存在"= TRUE |
| 要不要 NULL 那批行 | 不要 → NOT IN；要 → NOT EXISTS；最稳 → 先写 IS NOT NULL 再二选一 |
| 没有经理 ≠ 经理离职 | "空值"和"不存在"是两种语义，题目问的是哪个要想清 |
| 别名含空格/中文 | 一律加反引号 `AS `Low Salary`` |
| 题目给的是"行的值"还是"列名" | 先看 Output 示例是几行几列 —— 这决定了结果形状 |
| 某分类可能没有数据也要显示 0 | 用 COUNT(*)（空集返 0），别用 SUM（空集返 NULL） |
| 类别不在表里、由条件推导 | UNION ALL 分别统计，或先造类别集合再 LEFT JOIN |
| UNION ALL 做什么 | 把多条 SELECT 的结果**上下堆叠**（行相加），不是加列 |
| UNION vs UNION ALL | UNION 去重（要排序，慢）；互斥时一律用 UNION ALL |
| 堆叠的硬条件 | 列数相同、按**列位置**对齐、列名取第一个 SELECT |
| ORDER BY 位置 | 写在最后一条之后作用于整体；只作用于单条要加括号 |

> 新卡点随时往下加。**一行一条，只写"怎么写"，不写解释。**

- 识别信号：题目里出现 「…及其…」「…以及…」「…和…」 连着列好几个指标 → 就是这张模板。

```
SELECT 分组列,
       COUNT(*)                              AS 总数,
       SUM(条件)                             AS 满足条件的个数,
       SUM(数值列)                            AS 总金额,
       SUM(IF(条件, 数值列, 0))               AS 满足条件的金额
FROM 表
GROUP BY 分组列;
```

## 4. 书写顺序 vs 执行顺序（速记卡）

> **详细推导见 2.5**。这里只留口诀和三条硬规矩，供做题时扫一眼。

```
书写顺序：SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY
执行顺序：FROM → JOIN → ON → WHERE → GROUP BY → 聚合 → HAVING → SELECT → ORDER BY
```

**三条由此推出的规律**：

1. `WHERE` 里不能有聚合函数（聚合发生在 `GROUP BY` 之后）
2. `HAVING` 里可以有聚合函数
3. `WHERE` 管**行**，`HAVING` 管**组**

> 一句话记忆：**"先拼表，再筛行，再分组，再筛组，最后才挑列和排序。"**

## 5. 从结果反推错因（三种"结果长相"）

| 结果长相 | 病因 | 第一反应 |
|---|---|---|
| **多了不该有的行 + 少了该有的行** | 条件写反（`=` vs `!=`） | 看 `WHERE` |
| **0 行，但预期有行** | 条件恒假（类型不匹配 / 逻辑不可能） | 问"这条件有可能为真吗" |
| **右表列全 NULL，行数没少** | `ON` 一句都没生效（键写错 / 类型不符） | 看 `ON` 两边的列名 |
| **同一 id 出现多次** | 配对条件漏了（笛卡尔积） | 补 `ON`，或加 `DISTINCT` 兜底 |

### 连接键的判据

> **连接键在两张表里应该「同名」，或构成「`xxx_id` 对 `id`」的关系。**

| 写法 | 判定 |
|---|---|
| `p.product_id = s.product_id` | ✅ 同名 |
| `o.user_id = u.id` | ✅ `xxx_id` 对 `id` |
| `p.product_id = s.sale_id` | ❌ 两个不同编号 |
| `u.unique_id = e.id` | ❌ 拿业务字段当键 |

**动作**：写完 `ON`，指着两边各念一遍中文 —— **"产品编号 = 销售单号"，念出来就不对劲了。**

## 6. 判错后的排查顺序（别乱猜）

| 顺序 | 查什么 | 例子 |
|---|---|---|
| **1** | **读题**（`!=` vs `=`；"没有" vs "有"；"至少" vs "等于"） | 584 把 `!=2` 写成 `=2` |
| 2 | 逻辑（结果多了谁、少了谁 —— 用第 5 节） | |
| 3 | 格式（列名 / 列顺序 / 小数位） | 力扣最爱在这判错 |

> **判题系统只会在「格式」上冤枉你；逻辑错它永远是对的。**

## 7. 看完答案后必须做两件事

**① 拆骨架（5 行）**

```
SELECT   ← 它输出哪些列（别名、ROUND、聚合）
FROM     ← 主表是哪个？为什么是它？
JOIN     ← 挂了什么？配对键是什么？角色怎么区分？
WHERE    ← 筛掉了什么？
GROUP BY ← 按什么聚合？
```

**② 合上答案，从零重写一遍。写不出来 = 没懂，不算做过。**

## 10. 判断"真的会了"的标准

| 状态 | 判定 |
|---|---|
| 看着答案能看懂 | **不会**（最常见的自欺） |
| 合上答案能默写整段 | 会用，但不会变通 |
| **不看笔记，3 分钟内写出骨架 + 说出每个空填什么** | **会了** |
| 换个类似题目还能套出来 | 真的会了 |
