## 1.软件测试的定义与目的

### 定义

软件测试是评估软件产品质量、验证其是否满足规定需求的过程。通过发现缺陷、提供质量信息，帮助团队降低发布风险、做出发布决策。 注意：确认"功能按需求实现了"也是测试的产出（正向验证），不只是找错。（测试是找错和确认对。找错是在可能出现问题的地方主动找，确认对是确认该有的功能等没有出错。相当于是计算完成之后的验算。）

### 目的

提前发现缺陷并解决，避免在上线后造成损失。尽早发现问题，降低后续修改问题的代价

## 2.软件测试的 7 条基本原则（每条都要能各举一个例子）

1. **测试显示缺陷的存在，但不能证明缺陷不存在。**
    - 我的理解：测试更像抽检，只能证明抽到的部分，不能证明全部
    - 例子：日期加减天数正确，可能会有闰年、月末跨月等隐形缺陷；
    - 补充：测试能提高对软件质量的信心，但不能给出“无缺陷”的证明
2. **穷尽测试是不可能的。**
    - 我的理解：排列组合通常数量极大，数学上决定了穷尽法没可能
    - 例子：两个32位整数相加，有2的64次方种可能。
    - 补充：测试必须是基于风险的抽样：用等价类、边界值、组合测试、探索式测试、自动化回归等，在有限成本下覆盖最可能出问题的区域
3. **测试尽早介入。**
    - 例子：代码提交前跑静态扫描，发现空指针、SQL 拼接、资源未关闭、硬编码密钥。当天修复，成本远低于测试后期或上线后排查。
    - 补充：缺陷越早发现，修复成本越低，返工范围越小
4. **缺陷集群性（二八原则）**
    - 例子：一个电商系统一个迭代统计出 127 个缺陷：订单状态机 42 个 + 库存扣减 28 个 + 优惠券计算 19 个 = 89 个（占 70%）；而商品展示、用户资料、帮助中心三个模块合计只有 9 个。 所以下一轮测试应把 70% 的精力投在那三个模块。 但不能完全跳过其他区域 —— 集群性会随版本漂移（这轮没事的模块，下轮可能集中爆发）。
    - 补充：二八原则在软件测试里通常指：少数模块、功能、用例或场景集中了大多数缺陷。应做缺陷热点分析，集群性会随版本变化，不能只测热点而完全忽略其他区域；同时应追根因，避免只修表象
5. **杀虫剂悖论（同样的用例反复用会失效，用例会像害虫一样产生抗药性）**
    - 例子：一个输入框的 15 条回归用例连跑 20 个版本全绿。第 21 版，开发把提示语从"请输入手机号"改成了"手机号格式不正确"—— 用例仍然全绿，因为这 15 条用例从来没校验过提示语的具体文案，只校验了"是否弹出错误"。 要发现这个改动，必须新增一条"校验提示文案内容"的用例。
    - 补充：同一组测试用例反复执行，初期能发现不少缺陷，但随着缺陷被修复、产品变化、开发适应测试模式，这组用例发现新缺陷的能力会越来越弱
6. **测试活动依赖于测试背景。**
    - 例子：同一个"用户注册"功能 —— 在社交 App 里重点测体验和并发；在银行 App 里重点测实名合规、密码策略、审计日志；在医疗系统里还要满足监管验证要求。功能一样，测试重点完全不同；
    - 补充：背景决定风险，风险决定测试策略，测试活动不是越重越好，而是要与背景匹配。
7. **不存在缺陷的谬论。**
    - 例子： “没有缺陷”不等于“有价值”，没做错不等于做对了；
    - 补充：测试通过、缺陷清零，只能说明当前测试范围内未发现明显问题；不能证明需求正确、用户满意、业务成功、合规达标、性能可接受。

## 3.为什么「测试尽早介入」

要理解缺陷修复成本随阶段推移而陡增这条曲线：需求阶段发现 = 改一句话，上线后才发现 = 停机 + 修复 + 赔偿。

## 4.软件测试的层次

单元测试 → 集成测试 → 系统测试 → 验收测试（UAT）。每层分别测什么、由谁负责、在什么阶段做。

| 层次 | 测什么 | 谁负责 | 什么阶段 |
| --- | --- | --- | --- |
| 单元测试 | 代码做得对不对 | 开发者 | 编码阶段 |
| 集成测试 | 模块拼起来能不能通 | 开发 + 测试 | 编码完成后，持续集成中 |
| 系统测试 | 整个系统作为产品是否满足规格 | 独立测试 / QA 团队 | 完整系统构建后，发布前 |
| 验收测试 UAT | 业务是否愿意接受 | 用户 | 系统测试后，最终交付前 |

## 5.黑盒、白盒、灰盒测试的区别与各自适用场景

| 类型 | 是否看代码 | 关注点 | 适用阶段 |
| --- | --- | --- | --- |
| 黑盒 | 不看 | 只看输入输出、业务能否走通 | 系统测试、验收测试 |
| 白盒 | 深入了解 | 代码逻辑与内部结构 | 单元测试 |
| 灰盒 | 部分了解 | 介于两者之间 | 集成测试 |

## 6.完整的测试流程 6 个阶段，以及每个阶段的输入与输出

需求评审 → 测试计划 → 用例设计 → 用例执行 → 缺陷跟踪 → 测试报告

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| 需求评审 | 需求文档 / PRD | 评审意见、可测性评估、需求澄清记录 |
| 测试计划 | 需求 + 项目计划 | 测试计划（范围/策略/资源/进度/风险） |
| 用例设计 | 需求 + 设计文档 | 测试用例集 + 用例评审记录 |
| 用例执行 | 用例 + 测试环境 + 待测版本 | 执行记录、缺陷单 |
| 缺陷跟踪 | 缺陷单 | 状态流转记录、修复验证结论 |
| 测试报告 | 执行数据 + 缺陷数据 | 测试报告（结论、遗留缺陷、发布建议） |

## 7.缺陷从哪里来

- 需求不清
- 设计缺陷
- 编码错误
- 配置与环境差异
- 数据问题

## 8.测试分类

| 分类 | 测什么 |
| --- | --- |
| 功能 | 是否按需求和业务规则正确完成功能，含正常流程、边界、异常、权限 |
| 性能 | 特定负载下的响应时间、吞吐量、并发、资源消耗、稳定性 |
| 兼容性 | 不同系统、浏览器、设备、分辨率、网络、数据库、版本下能否正常工作 |
| 安全 | 能否防未授权访问、数据泄露、注入、越权、篡改，并满足合规要求 |
| 易用性 | 能否高效、低错误率、低学习成本完成任务，界面与可访问性是否友好 |
| 本地化 | 目标语言、地区的翻译、日期时间、货币格式、时区、法规适配 |
