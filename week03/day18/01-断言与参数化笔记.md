# Day 18 ｜ 断言与参数化

## 一、断言的四个层次

### 1.1 四层表（协议 / 结构 / 值 / 时间）

| 层 | 断言什么 | 例子 | 能发现什么 Bug |
| --- | --- | --- | --- |
| ① 协议 | 状态码、响应头 | to.have.status(200) | 接口挂了、路由错 |
| ② 结构 | 字段存在、类型、schema | to.have.jsonSchema(...) | 字段丢了、类型变了 |
| ③ 值 | 具体值对不对 | .to.eql("admin") | 数据算错、返回错人 |
| ④ 时间 | 响应耗时 | .to.be.below(500) | 性能退化 |

- ① 保证"能用"，② 保证"结构对"，③ 保证"结果对"。 三层都要有。

### 1.2 我改造后的 03-测试 POST（四层完整版，贴代码）

```js
pm.test("状态码是200", function () {
    pm.expect(pm.response.code).to.be.oneOf([200, 201]);
});
pm.test("服务器收到的是 POST", function () {
    pm.expect(pm.response.json().method).to.eql("POST");
});
const schema = {
    type: "object",
    required: ["method", "json", "headers"],
    properties: {
        method:  { type: "string" },
        json:    { type: "object" },
        headers: { type: "object" },
        url:     { type: "string" }
    }
};

pm.test("响应结构符合 schema", function () {
    pm.response.to.have.jsonSchema(schema);
});
```

④ 时间层（本地或测试环境才写）：
```js
// pm.test("响应小于 2s", function () {
//     pm.expect(pm.response.responseTime).to.be.below(2000);
// });
```

- 由于 httpbin 是公网接口，时间断言会随机失败，今天故意不写。

### 1.3 JSON Schema 的 required 管什么、不管什么

- `required`管 **不能少** ，一旦`required` 里写了但响应里没有 → FAIL
- `required`不管 **不能多**，响应里 多了字段 → 不 FAIL（schema 默认允许多余字段）

## 二、用变量组织断言

### 2.1 三种变量容器 + 什么时候用哪个

| API | 作用域 | 什么时候用 |
| --- | --- | --- |
| pm.collectionVariables | 整个集合 | 跨请求传递（最常用） |
| pm.environment | 当前环境 | 需要跟环境切换的值 |
| pm.variables | 一次请求内 | 临时计算 |
| pm.globals | 全局 | 别用（容易污染） |

## 三、参数化三件套

### 3.1 环境变量 / 动态变量 / 数据文件，各解决什么

| 类型 | 解决什么 | 例子 |

| 环境变量 | 换环境（dev/test/prod） | {{baseUrl}} |

## 四、数据驱动

### 4.1 什么是"一份用例跑 N 组数据"

```
用例：查询用户详情
数据：userId = 1, 2, 999
结果：跑 3 次，分别断言 200 / 200 / 404
```

- 用一条请求+N组数据可以断言N次

### 4.2 我的 users.csv（贴内容）

```
userId,expected
1,200
2,200
999,404
abc,400
```

### 4.3 为什么 Number() 不能省

- CSV 里读出来是字符串如果不加`Number()`，`status("200")`会失败

## 五、前置脚本

### 5.1 Before request vs After response

| 位置 | 什么时候跑 | 干什么 |
| --- | --- | --- |
| Before request | 请求发出前 | 准备数据、改 URL、加头 |
| After response | 响应回来后 | 断言（昨天写的） |

### 5.3 pm.variables.replaceIn 为什么必须用

| 位置 | {{$guid}} 会不会被解析 |
| --- | --- |
| 请求的 URL / Body | ✅ Postman 自动解析 |
| 脚本（Scripts）里 | ❌ 不会，它只是普通字符串 |

- 不写这一句，value 就是字面量 `"{{$guid}}"`，头会变成 `X-Request-Id: {{$guid}}`。
